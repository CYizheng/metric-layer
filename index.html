指标口径层

自然语言取数最容易出的错不是 SQL 写错，而是同一个词在不同人嘴里指不同东西。 「投递数」是投过就算，还是去掉已放弃的？「在流程中」包不包括泡池子？ 不把口径写下来，每次问出来的数都不一样，而且没人能证明哪个对。

一句问句怎么变成 SQL

自然语言
  ↓  ① 口径层命中（词典，确定性）
指标 · 维度 · 状态过滤 · 时间范围 · 排序限额
  ↓  ② 只从声明里拼装片段（不拼接任何用户原文）
SQL
  ↓  ③ 三层只读守卫
结果 + 译文 + 口径说明

词表是封闭的，所以命中结果可预测、可测试、可以被 review。

实际跑出来是什么样

$ python nlq.py -d data/demo.db --sql "本月各城市投递数"
问：本月各城市投递数
  解析：指标=投递数 · 分组=city · 时间=2026 年 10 月
  口径：只数投出去的记录，不区分当前状态。

  SELECT a.city AS "城市",
         COUNT(DISTINCT a.id) AS "投递数"
  FROM applications a
  WHERE a.applied_at >= '2026-10-01' AND a.applied_at < '2026-11-01'
  GROUP BY a.city
  ORDER BY 2 DESC
  LIMIT 200

  海口       5
  上海       4
  武汉       3
  深圳       3
  贵阳       3
  北京       2
  成都       2

  西安       1

  10 行 · 0.7 ms
$ python nlq.py -d data/demo.db --sql "各岗位类型的面试场次前3"
问：各岗位类型的面试场次前3
  解析：指标=面试场次 · 分组=category · 排序=降序 · 前 3
  口径：数的是事件流里的面试事件，一家单位可能面多轮，所以在这里 JOIN events。

  SELECT a.category AS "岗位类型",
         COUNT(DISTINCT e.id) AS "面试场次"
  FROM applications a
  LEFT JOIN events e ON e.app_id = a.id
  WHERE e.kind = '面试'
  GROUP BY a.category
  ORDER BY 2 DESC
  LIMIT 3

  岗位类型  面试场次
  ────────  ────────
  产品运营        18
  数据治理        12
  数据分析        11

  3 行 · 0.5 ms

第二个问句跨到了事件表——「面试场次」数的是事件流里的面试事件， 一家单位可能面多轮。这类跨表指标必须在口径层里显式声明，工具不会自己猜。

只读是三层，不是一句 if

层手段兜住什么
连接层 file:...?mode=ro + PRAGMA query_only=ON 即使判断逻辑被绕过，也写不进去
语句层 必须单条 SELECT／WITH；禁用 INSERT / UPDATE / DELETE / DROP / ALTER / ATTACH / PRAGMA / VACUUM 注入与误操作
结果层 没有 LIMIT 就自动补；fetchmany(max+1) 判断截断 一条误写把内存打爆

判断前先剥掉注释与字符串字面量，否则字段值里出现 drop 就会被误杀。

为什么不让模型当主力

模型（可选 Ollama）只处理规则层覆盖不到的复杂句，每一条输出都必须过守卫、 真跑一次，失败就报错回退。把「能不能查对」押在 CPU 上的 3B 模型上， 是这个工具最不该做的设计——它生成得快，但你没法证明它对。
